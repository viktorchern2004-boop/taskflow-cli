# Вимоги до Agent Harness для TaskFlow CLI

## 1. Мета

Agent Harness – інженерна інфраструктура, яка забезпечує AI-агента контекстом про застосунок TaskFlow CLI, формалізованими процедурами розробки (skills) і обмеженнями (guardrails). Сам harness не є бізнес-логікою застосунку.

**Результат:** відтворювані зміни коду; дотримання архітектури; безпечні операції; накопичення знань і оцінювання результатів роботи агента.

## 2. Архітектура та репозиторії

Harness працює у двох **окремих** git-репозиторіях:
1. `taskflow-cli` – код застосунку, вимоги, MCP-сервер, guardrails, hooks, skills, сценарії оркестрації.
2. `taskflow-knowledge-base` – Obsidian vault із нотатками `Concepts/`, `Components/`, `Decisions/`, `Glossary/` та MOC.

Vault зберігається **поза робочою директорією** агентної IDE, яка відкриває лише `taskflow-cli`. Агент читає й змінює vault **тільки через MCP-інструменти** `search_notes` / `get_note` та `ingest_note`. Окремий локальний процес MCP-сервера має доступ до клону vault за налаштованим шляхом.

```text
VS Code + GitHub Copilot Agent
├── Вбудовані інструменти файлів, термінала та git → taskflow-cli
├── GitHub MCP (read-only) → історія комітів, issues, pull requests
└── Власний vault MCP
    ├── search_notes / get_note → читання Obsidian-нотаток
    └── ingest_note          → створення/оновлення Obsidian-нотаток
                                   ↓
                       taskflow-knowledge-base (окремий клон)
```

## 4. Цільові автономні задачі (5)

1. **Генерація модулів.** За вимогами створювати невеликі модулі й команди TaskFlow CLI, дотримуючись архітектури; цінність – швидша реалізація.
2. **Генерація unit-тестів.** Створювати перевірки типових і граничних випадків, запускати їх; цінність – менше регресій.
3. **Рев'ю коду.** Перевіряти зміни на відповідність функціональним вимогам, стилю та guardrails; цінність – контроль якості.
4. **Підтримка документації.** Після змін коду оновлювати Markdown-описи та сценарії перевірки; цінність – актуальність документації.
5. **Документування ADR.** Формувати нотатки про архітектурні рішення та передавати їх через MCP у vault; цінність – накопичення знань без дублювання.

## 5. Первинні guardrails

Наведені категорії визначають межі **автономних дій агента**. Детальні перевірювані правила та програмні hooks реалізуються в ПР4.

### Allow – дозволено без підтвердження
- Читати вихідний код, вимоги, тести й історію комітів.
- Викликати `search_notes` для отримання знань із vault.
- Виконувати безпечні локальні команди аналізу та перевірки.

### Warn / Require approval – потрібне погодження людини
- Змінювати бізнес-логіку в `src/`, перейменовувати модулі або змінювати залежності.
- Створювати та оновлювати нотатки через `ingest_note`.
- Створювати коміти та пушити зміни до робочої гілки.

### Block – заборонено
- Робити прямий push у `main` замість перевіреного pull request.
- Видаляти історію нотаток у `Decisions/` через MCP.
- Додавати токени, ключі та інші секрети до Git.
- Виконувати деструктивні команди, що знищують репозиторій чи його історію.

**Уточнення:** початкове ручне створення репозиторію та першого коміту на ПР1 передує впровадженню guardrails; правила стосуються подальших автономних змін агента.

## 6. Компоненти Harness за практичними

| Робота | Компонент | Артефакт |
| --- | --- | --- |
| №1 | Проєктування | Вимоги до застосунку й harness |
| №2 | Knowledge layer | Окремий Obsidian vault із 8–10 нотаток та MOC |
| №3 | Data connectors | Власний vault MCP і GitHub MCP |
| №4 | Guardrails | Правила allow/warn/block і pre-tool-use hook |
| №5 | Skills | Два формалізовані skills |
| №6 | Orchestration | Цикл Planner → Coder → Reviewer, журнал handoff |
| №7 | Evaluation / RAG | Embeddings, локальний індекс та тестування на однакових питаннях |

## 7. Оцінювання Harness

- **Успішність задач:** частка завершених тестових задач.
- **Порушення guardrails:** кількість недозволених операцій (ціль – нуль).
- **Ідемпотентність MCP ingestion:** повторний однаковий виклик не створює дублікати.
- **Якість retrieval:** коректність відповідей на 8–10 однакових запитів до й після RAG.
- **Відтворюваність:** результати тестів, журнали оркестрації та коміти фіксуються.

## 8. Основні обмеження й ризики

- У агента немає прямого файлового доступу до vault за межами MCP.
- GitHub MCP використовує мінімальні необхідні права (для джерел даних – лише читання).
- Секрети не зберігаються в репозиторії; залежності та інструменти перевіряються перед установленням.
- Локальний векторний індекс у ПР7 – похідний артефакт, не є джерелом істини; його каталог додається до `.gitignore`.
- Конкретну підтримку skills/hooks/subagents в обраній IDE треба підтвердити на встановленій версії перед практичними №3–6.
