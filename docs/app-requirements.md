# Вимоги до застосунку TaskFlow CLI

## 1. Загальна характеристика
**Тип:** локальний консольний застосунок (CLI) для обліку особистих завдань.  
**Користувачі:** студенти й індивідуальні користувачі.  
**Обсяг:** один користувач, локальний JSON-файл, без вебінтерфейсу, авторизації й хмарної синхронізації.

## 2. Функціональні вимоги

| ID | Функція | Критерій приймання |
| --- | --- | --- |
| FR-01 | Додати завдання | `add` повертає унікальний ID; порожня назва відхиляється. |
| FR-02 | Переглянути завдання | `list` показує всі записи; `show <ID>` повертає потрібний запис. |
| FR-03 | Редагувати завдання | `update <ID>` змінює лише передані поля. |
| FR-04 | Змінити статус | Дозволені `todo`, `in_progress`, `done`. |
| FR-05 | Змінити пріоритет | Дозволені `low`, `medium`, `high`; початковий – `medium`. |
| FR-06 | Установити дату | Коректну дату формату `YYYY-MM-DD` прийнято, некоректну відхилено. |
| FR-07 | Фільтрувати список | Параметри `--status` і `--priority` обмежують результати `list`. |
| FR-08 | Видалити завдання | `delete <ID>` вимагає підтвердження, крім випадку `--yes`. |
| FR-09 | Зберігати записи | Після перезапуску завдання відновлюються з локального JSON-файлу. |

**Модель завдання:** `id`, `title`, `description`, `status`, `priority`, `due_date`, `created_at`, `updated_at`.

## 3. Нефункціональні вимоги

| ID | Вимога | Як перевірити |
| --- | --- | --- |
| NFR-01 | Автономність | Основні команди не потребують доступу до мережі. |
| NFR-02 | Продуктивність | Операції зі списком до 1000 записів на типовому ПК орієнтовно тривають до 1 с. |
| NFR-03 | Коректність даних | Некоректне введення й пошкоджений JSON не призводять до мовчазної втрати даних. |
| NFR-04 | Тестованість | Бізнес-логіка перевіряється за допомогою `pytest`. |
| NFR-05 | Безпека | Файли з особистими даними та секретами виключені з Git. |
| NFR-06 | Супроводжуваність | Команди CLI, моделі, логіка та збереження даних рознесені по модулях. |

## 4. Технологічний стек

- **Python 3.11+** та `argparse`, `json`, `pathlib`, `datetime`, `uuid`.
- **pytest** – автоматизовані модульні тести на наступних етапах.
- **Git / GitHub** – версіювання, історія комітів, pull requests.
- **Obsidian** – окрема база знань із практичної №2.
- **MCP** – доступ агента до vault і даних GitHub із практичної №3.

## 5. Обрана агентна IDE

**Visual Studio Code з GitHub Copilot Chat у режимі Agent.** Дає вбудовані інструменти редагування коду, термінал, Git та підтримку MCP-серверів. В актуальних сумісних версіях доступні також проєктні інструкції, skills, custom agents і hooks. Перед практичними №3–6 треба перевірити конкретну встановлену версію й права тарифу.

**Обґрунтування:** сумісність із Python, підтримка зовнішніх MCP-інструментів, можливість виконання bash/термінальних команд, інструкцій і перехоплення дій для реалізації guardrails.

## 7. Послідовність реалізації

- **ПР1:** документація й два репозиторії.
- **ПР2:** Obsidian vault з 8–10 нотаток, wiki-зв'язками та MOC.
- **ПР3:** базовий MCP-конектор для vault і GitHub MCP; перші модулі застосунку.
- **ПР4:** деталізація guardrails та hook.
- **ПР5:** два skills для повторюваних задач розробки.
- **ПР6:** Planner → Coder → Reviewer для нової функції.
- **ПР7:** векторний пошук і порівняння 8–10 відповідей до/після RAG.

## 8. Критерії готовності

1. Реалізовано FR-01 – FR-09 або задокументовано причини відхилень.
2. Основні сценарії підтверджено тестами.
3. Код, документація й історія змін зберігаються у GitHub.
4. Доступ агента до окремого vault здійснюється лише через власний MCP-конектор.
